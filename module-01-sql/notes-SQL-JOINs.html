autosys_jobs
The robot alarm clock
At Meridian Systems, hundreds of computer tasks run automatically every night — sorting numbers, moving files, generating reports. Autosys is the system that schedules and runs these tasks. It keeps a list of every task (called a "job") and writes down whether it finished successfully or broke. Our autosys_jobs table is that list.
🎫
servicenow_tickets
The help-desk notebook
When something breaks at Meridian Systems, the support team creates a "ticket" — a note that says what broke, how urgent it is, and who is working on it. ServiceNow is the system that stores all these tickets. Our servicenow_tickets table is that notebook of problems and who is fixing them.
The scenario

Two notebooks, one connection

Autosys keeps a list of every job that ran. ServiceNow keeps a list of every ticket raised when something went wrong. These two lists live in separate systems — but both care about the same jobs. When a job fails in Autosys, a ticket is raised in ServiceNow with the same job_id. That shared column is how we connect them.

Think of job_id like a student's ID number. If both the attendance sheet and the report card use the same student ID, a teacher can look up a student across both sheets — even though the sheets were made separately.

01
Why JOINs exist ▾

Imagine two physical notebooks on your desk. If you want to answer "which tickets belong to which failed job?" — you'd have to flip between notebooks, match up the job IDs, and write down the combined information yourself. That's painful with 5 rows. It's impossible with 5 million.

A JOIN is SQL's way of doing that combination automatically. You tell it: "look at these two tables, find rows where the job_id matches, and stitch those rows together into one result."

The four types of JOIN only differ in one question: what do we do when a match doesn't exist on one side? Each type answers that differently.

02
Primary key vs foreign key ▾
primary key
The unique ID that belongs to a table. In autosys_jobs, job_id is the primary key — every job has exactly one, and no two jobs share the same one. It's like a passport number.
foreign key
When that same ID appears in a second table as a reference. In servicenow_tickets, job_id is a foreign key — it's saying "this ticket belongs to that job over there." It's the bridge between the two tables.
ON condition
ON aj.job_id = sn.job_id — this is the instruction that tells SQL: "match rows from both tables wherever these two columns have the same value."

The autosys_jobs table owns the job_id. Every other table that references a job borrows that ID. The JOIN reunites them.

03
INNER JOIN ▾
Plain English: "Only show me rows that exist in both lists at the same time."
blue region = rows returned · grey region = rows dropped
SELECT aj.job_id, aj.job_name, aj.status, sn.ticket_id, sn.priority FROM autosys_jobs AS aj INNER JOIN servicenow_tickets AS sn ON aj.job_id = sn.job_id;

From our Meridian data: JOB005 disappears — it has no matching ticket, so INNER JOIN drops it entirely. JOB001 appears twice because it matched two tickets (INC001 and INC003). Result: 5 rows.

04
LEFT JOIN most used ▾
Plain English: "Show me every row from the left list. For each one, add ticket info if it exists. Write NULL if it doesn't."
entire left circle = all returned · right side fills in where a match is found
SELECT aj.job_id, aj.job_name, aj.status, sn.ticket_id, sn.priority FROM autosys_jobs AS aj LEFT JOIN servicenow_tickets AS sn ON aj.job_id = sn.job_id;

From our Meridian data: JOB005 now stays in the result — with NULL written in the ticket columns because no matching ticket exists. JOB001 still appears twice. Result: 6 rows.

This is the JOIN you will write most often. When you're unsure which JOIN to use, start here.

05
RIGHT JOIN rarely written ▾
Plain English: "Show me every row from the right list. Add job info where it exists. Write NULL where it doesn't."
entire right circle = all returned · left side fills in where a match is found

Every RIGHT JOIN can be rewritten as a LEFT JOIN by swapping which table comes first. Most analysts just flip the tables and always write LEFT JOIN. Know that RIGHT JOIN exists — but you will almost never write it.

06
FULL OUTER JOIN ▾
Plain English: "Show me absolutely everything from both lists. Fill in NULL wherever there is no match on either side."
both circles = everything returned · NULL appears on whichever side has no match
SELECT aj.job_id, aj.job_name, aj.status, sn.ticket_id, sn.priority FROM autosys_jobs AS aj FULL OUTER JOIN servicenow_tickets AS sn ON aj.job_id = sn.job_id;

From our Meridian data: JOB005 appears with NULLs on the ticket side (no match). All 5 tickets appear. JOB001 still appears twice. Result: 6 rows.

07
The NULL pattern — finding what's missing ▾
Pattern: LEFT JOIN + WHERE right_key IS NULL → "find rows in the left table with nothing matching on the right"

Think of it like this: a teacher has an attendance sheet and a homework submission pile. LEFT JOIN combines them. WHERE submission IS NULL finds exactly which students didn't hand anything in.

-- Which jobs ran with no ticket ever raised? SELECT aj.job_id, aj.job_name, aj.status FROM autosys_jobs AS aj LEFT JOIN servicenow_tickets AS sn ON aj.job_id = sn.job_id WHERE sn.ticket_id IS NULL;

This returns only JOB005. The LEFT JOIN kept it in the result with NULLs. The WHERE then says "only show me the ones where the ticket side is empty."

You will use this constantly: customers who never ordered, employees with no review, students who didn't submit. The pattern is always the same — LEFT JOIN, then WHERE right_key IS NULL.

Self-check — 5 questions
You want every job from autosys_jobs, including ones with no ticket. Which JOIN type?
Q1
LEFT JOIN. The left table (autosys_jobs) is guaranteed to fully appear in the result. Jobs with no matching ticket show NULL in the ticket columns instead of being dropped.
An INNER JOIN returns 5 rows. A LEFT JOIN on the same tables returns 7. What do those extra 2 rows mean?
Q2
There are 2 rows in the left table with no match in the right table. INNER JOIN quietly dropped them. LEFT JOIN kept them, filling the right-side columns with NULL.
Why does JOB001 appear twice in a JOIN result, even though it only exists once in autosys_jobs?
Q3
JOB001 matched two rows in servicenow_tickets — INC001 and INC003. A JOIN creates one output row for every match it finds. One job matched twice = two output rows. This is called a one-to-many relationship.
Describe in plain words the pattern for finding jobs that never had a ticket raised.
Q4
LEFT JOIN servicenow_tickets on job_id, then add WHERE sn.ticket_id IS NULL. The LEFT JOIN keeps all jobs even those with no ticket. The IS NULL filter then isolates only the unmatched ones — the ones the JOIN filled with NULL on the right side.
You have a RIGHT JOIN. How do you rewrite it as a LEFT JOIN without changing the result?
Q5
Swap the table positions — move the right table into FROM, move the left table into the JOIN clause, then change RIGHT JOIN to LEFT JOIN. The result is identical. This is why most analysts just always use LEFT JOIN.
